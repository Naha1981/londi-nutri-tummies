PART 8 — SECURITY ARCHITECTURE
Every security boundary must fail closed.
Authentication
•	Bad: No secret? Accept request.
•	Good: No secret? Reject request.
Authorization — Always verify:
•	Who is making this request?
•	What are they allowed to access?
•	Which tenant owns this resource?
Never trust:
•	tenant IDs from arbitrary clients
•	account ownership claimed in webhook payloads
•	user role claims without verification
•	query parameters as proof of identity
Derive ownership from authoritative database relationships — not client-supplied data.
________________________________________
PART 9 — WEBHOOKS
For every webhook:
1.	Verify signature.
2.	Fail closed.
3.	Use constant-time comparison where appropriate.
4.	Validate payload structure.
5.	Derive ownership from trusted records.
6.	Implement idempotency.
7.	Handle retries safely.
8.	Avoid duplicate side effects.
VERIFY → VALIDATE → RESOLVE AUTHORITATIVE OWNERSHIP →
CHECK IDEMPOTENCY → RECORD EVENT → PROCESS → RETURN CLEAR RESPONSE
Never generate irreversible side effects before idempotency is established.
________________________________________
PART 10 — DATABASE ENGINEERING
Before changing the schema, determine:
Does existing data remain valid?
Does the migration lock the table?
Is the change additive?
Can old and new code coexist during rollout?
Does deployment ordering matter?
Is rollback possible?
Are indexes required?
Are uniqueness constraints required?
Prefer additive migrations, e.g. ADD COLUMN IF NOT EXISTS.
Use nullable columns for backward compatibility where appropriate, apply defaults carefully, use partial indexes where appropriate, and enforce real invariants with unique constraints.
Critical invariants belong in the database — never rely only on application-level race prevention.
________________________________________
PART 11 — IDEMPOTENCY AND CONCURRENCY
Assume systems will retry. Assume:
•	webhooks duplicate
•	workers restart
•	networks time out
•	processes crash
•	requests overlap
•	queues deliver more than once
Use: Idempotency keys · Unique constraints · UPSERT / ON CONFLICT · Outbox pattern · Transactional boundaries
Ask: What happens if this operation runs twice? Then: What happens if two copies run simultaneously?
________________________________________
PART 12 — OUTBOX AND ASYNCHRONOUS WORK
For external side effects:
DATABASE EVENT → DURABLE JOB → WORKER → EXTERNAL SYSTEM → SUCCESS/FAILURE RECORDED
Do not make a database write appear successful if the external action silently disappeared. Every important asynchronous operation should have observable state: pending → processing → queued → sent → delivered → failed.
Do not display success unless success is actually known.
________________________________________
PART 13 — UI TRUTHFULNESS
The UI must reflect reality. Never show ✓ Delivered unless delivery is known. Use explicit states: Sending / Queued / Delivered / Failed / Unknown.
Historical data without a known state should remain unknown — do not fabricate green indicators.
________________________________________
PART 14 — ERROR HANDLING
Every critical failure should answer:
What failed?
Why did it fail?
Can the user act on it?
Can the system retry?
Will the failure be visible?
Avoid return { ok: true } when nothing actually happened. Success must mean the defined success contract occurred — not merely that no exception was thrown.
________________________________________
PART 15 — TESTING PYRAMID
Test every significant change at the appropriate level.
Unit tests — pure logic (Input → Decision → Output)
Integration tests — components together (API → Service → Database)
Seam tests — confirm real modules are actually wired together:
Route → Dispatch helper → Outbox → Worker → Database state → UI
Seam tests prevent: "The helper works perfectly, but the real route never calls it."
________________________________________
PART 16 — FAILURE TESTING
Do not test only happy paths. Deliberately simulate:
Missing environment variable    Timeout                Null foreign key
Invalid secret                  Duplicate webhook       Worker crash
Database unavailable            Disconnected account    Retry exhaustion
External API failure            Malformed payload       Unauthorized user
                                                          Race condition
The most important test is often: the exact failure that caused the last bug.
________________________________________
PART 17 — MUTATION TESTING MINDSET
For critical logic, deliberately break it:
Change success to true.
Disable a guard.
Remove a condition.
Skip reconciliation.
Treat "queued" as "delivered."
Then confirm the tests fail. The stronger question isn't "Do tests pass?" — it's "Would the tests catch the bug returning?"

PART 20 — SELF-HOSTED TOOLS POLICY
Evaluate every new tool in this order:
1. Can we use the existing stack? Don't add infrastructure unnecessarily.
2. Open source / self-hosted — prefer when: recurring SaaS cost is significant, sensitive data should stay under our control, the tool is core infrastructure, vendor lock-in is dangerous, or deployment complexity is acceptable.
3. Managed services — prefer when: uptime burden exceeds our operational capacity, security operations are complex, the service isn't our competitive advantage, or self-hosting would cost more in engineering time than it saves.
Self-host strategically. Do not self-host for ego.

PART 25 — HEALTH VS. READINESS
Do not confuse the two.
Liveness — Is the process alive? → /health
Readiness — Can this service actually perform its job? → /ready

PART 26 — CRON AND SCHEDULER VERIFICATION
A cron route existing does not mean cron is running. For every scheduled job, verify the full chain:
Endpoint exists → Correct HTTP method → Auth works → Unauthorized calls fail →
Authorized calls succeed → Scheduler is configured → Scheduler history shows
repeated success → Jobs actually process → Queue depth stays healthy
Configured ≠ running. Running ≠ processing. Processing ≠ succeeding. Verify the entire chain.

## 0. Prime Directive

Build every application as a **modular, AI-native, full-stack monolith** on Next.js App Router, deployed serverlessly on Vercel, organized by business domain, with clean module boundaries that permit later extraction.

**One repo. One deployment. One database. One auth provider. One AI SDK. One WhatsApp platform. One deployment target.**

Split into microservices only when production metrics prove it necessary (e.g., stateful WebSocket connections). Never pre-emptively. You are one person. Complexity is your enemy.

Optimize, in order, for:
1. **Correctness and security** — it must work and it must be safe
2. **Development velocity** — you must be able to build fast with AI assistance
3. **Low total cost of ownership** — free tiers first, pay only when revenue justifies it
4. **Enterprise scalability** — via extraction-ready design, not premature distribution
5. **Maintainability** — future-you (or a future AI session) must understand it

### The mental model
- One repository. One deployment. One production URL.
- One backend (Route Handlers + Server Actions). One database (Neon PostgreSQL).
- One auth provider (Clerk). One AI SDK (Vercel AI SDK). One WhatsApp platform (NahaLabs Messaging Platform).
- Many integrations — all webhook-first, all wrapped in typed clients, all swappable.

## 1. The Stack — One Choice Per Layer, No Alternatives

Every project uses this exact stack. No "or Prisma if justified." No "or Auth.js." No "or Supabase." One tool per job. Fewer decisions = fewer mistakes.

| Layer | The One Choice | Why This One |
|---|---|---|
| **Framework** | Next.js (latest, App Router) + TypeScript (strict) | Frontend AND backend in one repo. One `npm run build`. One deploy. |
| **UI** | Tailwind CSS + shadcn/ui | Design tokens, no ad-hoc colors, consistent look across all your apps. |
| **Forms / Validation** | React Hook Form + Zod | Zod schemas shared client/server. One schema, two uses. |
| **Client data fetching** | TanStack Query | Never fetch in `useEffect`. Cache, retry, and loading states for free. |
| **Client state** | Zustand — only when server state isn't enough | Prefer server state. Add Zustand only for genuinely client-only state. |
| **Database** | Neon PostgreSQL | Serverless, free tier, connection pooling, pgvector-ready. One database for everything. |
| **ORM** | Drizzle ORM (or Prisma) | Typed queries, simple idempotent schema sync. |
| **Auth** | **Clerk** (and nothing else) | Prebuilt sign-in/up, session management, middleware gating, free for 10k MAU. Zero custom auth code. Ever. |
| **AI** | Vercel AI SDK | Provider-agnostic (OpenAI, Gemini, Claude, Groq, etc.), streaming, tool calling. One SDK, any model. |
| **File storage** | Vercel Blob | Managed, no infra, no S3 buckets to configure. |
| **Payments** | PayFast / Stripe behind a common abstraction | Webhooks are payment truth. Browser redirects are never confirmation. |
| **WhatsApp** | **NahaLabs Messaging Platform (Custom Baileys Operator)** | 2-Server architecture (ADR-014). Core App (Vercel) + Stateful Operator (Render). Account-scoped sessions, HMAC v2, Outbox pattern. Free, self-owned. |
| **Email** | Provider-abstracted client (optional) | Resend, Gmail SMTP, or SES — swap one file. Email is secondary; WhatsApp is primary. |
| **Deployment** | Vercel (Core) + Render (Operator) | Serverless for core app. Stateful Docker container for WhatsApp WebSockets. |
| **Background workers** | Vercel Cron + PostgresWorker | Durable jobs via `FOR UPDATE SKIP LOCKED`. |
| **E2E testing** | Playwright | Real browser, real clicks, real assertions. **Run against production, not just localhost.** |
| **Version control** | GitHub | One repo per app. GitHub Actions for CI. |

**Never** create a separate FastAPI / Express / NestJS / Django backend for business logic. **Never** use a different database. **Never** use a different auth provider. **Never** use third-party WhatsApp bridges (Evolution API, Twilio, 360dialog) or SaaS conductors (NoClick).

### Module contract
Every module owns its: service functions (business logic), Zod validation schemas, database access, types, events emitted, and tests. Modules communicate via **exported service functions and events — never by reaching into each other's tables.**

### The Single Authority Rule
**Every file has exactly one owner.** When an AI session creates or modifies a file, it must not create a *parallel* version of an existing component. If a component needs changing, **edit the existing file** — never create `Hero-v2.tsx` alongside `Hero.tsx`. If you're unsure whether a component already exists, **search first, create second.**

## 4. AI-First Architecture

## 6. Integration Architecture

**Every external system connects through a dedicated integration client and terminates at a dedicated webhook route.**

### NahaLabs Messaging Platform (WhatsApp) Standard (ADR-014)
We do not use third-party WhatsApp bridges or SaaS conductors. We own the infrastructure via a custom 2-Server Microservice Architecture.

**The Architecture:**
1. **Core App (Next.js on Vercel):** Handles UI, AI brain, Prisma database, outbox, and durable jobs.
2. **WhatsApp Operator (Express + `@whiskeysockets/baileys` on Render):** A stateful Docker service that maintains persistent WebSocket connections to WhatsApp.
3. **The Bridge (HMAC v2 Webhooks):** Core and Operator communicate exclusively via signed HTTP endpoints.

**Database Split (Crucial):**
- **Core App:** Uses Prisma/Drizzle for all business data (`tenants`, `messages`, `OutboxMessage`, `PlatformJob`).
- **Operator:** Uses raw `pg` (node-postgres) for Baileys auth sessions (`wa_sessions` table) to handle `BufferJSON` serialization. The Operator auto-creates its tables on boot.

**Identity & Multi-Tenancy:**
- Fundamental identity is `wa_account_id` (one connected WhatsApp number).
- One credential state per account (`wa_sessions` PK: `wa_account_id, key`).
- **INV-1:** ONE live socket per `wa_account_id`, regardless of how many apps/tenants bind to it.
- Bindings (`wa_account_bindings`) map `(app_id, tenant_id)` to a `wa_account_id`.

**Inbound Flow (Customer → AI):**
1. Operator receives message → persists `platform_event` → creates idempotent `inbound_delivery` per active binding.
2. Operator fires signed webhook (HMAC v2: timestamp + nonce + raw body signature) to Core App.
3. Core App verifies HMAC → persists inbound message → enqueues `PlatformJob` → returns 200 fast.
4. Durable Job Worker (PostgresWorker with `FOR UPDATE SKIP LOCKED`) processes job → runs AI Revenue Employee (Vercel AI SDK) → writes reply to `OutboxMessage`.

**Outbound Flow (AI → Customer):**
1. Outbox Dispatcher worker polls `OutboxMessage` (with `SKIP LOCKED`).
2. Calls Operator `/send` endpoint (signed with HMAC v2).
3. Operator sends via Baileys socket → updates delivery status → retries with backoff → dead-letters after 5 attempts.

**Security & Observability:**
- HMAC v2 on all Core ↔ Operator traffic. Constant-time comparison (`crypto.timingSafeEqual`).
- QR codes are ephemeral (Redis/in-memory TTL), never stored in Postgres.
- Trace envelope on all logs: `traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`.
- Business code calls `sendMessage(...)` via a typed client (`src/lib/messaging/platform-client.ts`). It never imports Baileys or transport-specific methods.

### Payments standard
- Providers (PayFast, Stripe) live behind a common payment abstraction.
- **Browser redirects are never payment confirmation. Provider webhooks are the sole source of truth.** Verify signature, source, and amount before updating order state.

# How the NahaLabs Messaging Platform Actually Works (Plain English)

Imagine you own a hair salon. A customer WhatsApps your business number asking "How much for balayage?"

Here's exactly what happens in the next 3 seconds:

---

## The Two-Server Setup (Like a Restaurant)

Think of it like a restaurant with a **front-of-house** and a **back-of-house**:

**1. The Front-of-House (Vercel - Your Main App)**
- This is what you and your staff see: the dashboard, the AI brain, the customer database, the payment system
- It's like the dining room and the manager's office
- It's fast, stateless, and runs on Vercel (serverless)

**2. The Back-of-House (Render - The WhatsApp Operator)**
- This is a dedicated server that stays logged into WhatsApp 24/7 (using Baileys, the same library WhatsApp Web uses)
- It's like the kitchen — it handles the heavy, persistent work of actually sending and receiving WhatsApp messages
- It runs on Render (a Docker container that never sleeps)

**They talk to each other via secure, signed webhooks** (like a kitchen ticket system with security seals).

---

## What Happens When a Customer Messages You

**Step 1: Customer sends a message**
- Customer texts "How much for balayage?" to your salon's WhatsApp number

**Step 2: The Back-of-House receives it**
- The WhatsApp Operator (on Render) is logged into your WhatsApp account and sees the message instantly
- It records the message in a database table called `platform_events`
- It checks which apps are allowed to see this message (in your case, just 2ndLife for your salon)

**Step 3: The Back-of-House sends a secure ticket to the Front-of-House**
- The Operator creates a signed webhook (like a tamper-proof receipt with a timestamp and security code)
- It sends this to your main app on Vercel via a webhook endpoint

**Step 4: The Front-of-House verifies and processes**
- Your main app receives the webhook
- It verifies the security signature (HMAC v2) to make sure it's really from your Operator and not a hacker
- It saves the inbound message to your database
- It creates a "job" for the AI to process (like putting an order ticket on the kitchen rail)

**Step 5: The AI Brain thinks**
- A background worker picks up the job
- It loads your salon's "Business Brain" (your services, prices, brand voice, compliance rules)
- It calls the Vercel AI SDK (which routes to GPT-4o-mini or another model)
- The AI generates a reply: "Balayage starts at R1,200 for medium-length hair. Would you like to book a consultation?"

**Step 6: The reply goes to the Outbox**
- The AI's reply is saved to an `OutboxMessage` table with status "queued"
- This is like putting the finished dish on the pass, ready to be served

**Step 7: The Outbox Dispatcher sends it**
- A worker polls the outbox every minute (via cron-job.org or Vercel Cron)
- It picks up your queued message
- It sends a signed request back to the WhatsApp Operator: "Send this text to +27821234567"

**Step 8: The Back-of-House delivers it**
- The Operator receives the request, verifies the signature
- It uses the Baileys socket (still logged into your WhatsApp) to send the message
- The customer sees the reply in their WhatsApp app

**Total time: 2-5 seconds from customer message to AI reply.**

---

## How Multi-Tenancy Works (Why This Scales)

Imagine you have 100 salon clients, each with their own WhatsApp number.

**The magic is in the `wa_account_id`:**
- Each WhatsApp number gets a unique account ID
- The Operator maintains **one live socket per account** (so 100 sockets total)
- Each socket is locked with a Redis key so if you restart the server, only one instance can claim each socket (prevents duplicate connections)

**Bindings map accounts to tenants:**
- Your salon's WhatsApp account (`wa_account_id: "abc123"`) is bound to your tenant (`tenant_id: "salon-456"`)
- When a message comes in, the Operator checks the bindings table to know which app/tenant should receive it
- Your salon's data never touches another salon's data (tenant isolation at the database level)

**What happens if you launch a second app (Flavourly)?**
- Flavourly can bind to the **same** WhatsApp account
- When a message comes in, the Operator fans out the delivery to both 2ndLife and Flavourly
- Each app processes the message independently with its own AI and business logic
- One WhatsApp number, multiple apps — no duplicate sockets

# UNIVERSAL WHATSAPP ARCHITECTURE (Direct / No Twilio)

**Role for AI:** You are an expert backend architect building a multi-tenant SaaS with a direct, un-official WhatsApp Web integration. You will **never** use Twilio, Evolution API, 360dialog, or paid WhatsApp Cloud APIs. You will use the "Linked Devices" WebSocket architecture.

## 1. The Two-Component Split (Crucial Rule)
Never put the WhatsApp socket connection in the same codebase/host as the serverless frontend.
*   **The Brain (Main App):** Next.js on Vercel (Serverless). Handles UI, Auth (Clerk), Database (Neon/Postgres), Tenant isolation, AI logic, and Webhook receivers.
*   **The Engine (Operator):** Node.js + `@whiskeysockets/baileys` on Render/Docker/Fly.io (Persistent). Holds the 24/7 WebSocket connection to WhatsApp. Survives server restarts.

## 2. The Engine (Operator) Responsibilities
*   **Auth:** Generates QR codes for Linked Devices. Saves the cryptographic session state (creds) encrypted into the Main App's database.
*   **Listening:** Listens to the WhatsApp WebSocket. When a message arrives, it forwards it to the Main App.
*   **Sending:** Exposes a REST API (`POST /send`) so the Main App can tell it to deliver a message.
*   **Health:** Exposes `GET /health` for the Main App to monitor uptime.

## 3. The Handshake (Security & Communication)
*   **Engine to Brain (Inbound):** The Operator `POST`s inbound messages to the Main App's webhook (`/api/webhooks/whatsapp`). **Must be secured with HMAC-SHA256 signatures** so the Brain knows the message is real and not spoofed.
*   **Brain to Engine (Outbound):** The Main App sends messages by calling the Operator's REST API. Secured via a shared `OPERATOR_API_KEY` in the headers.

## 4. Multi-Tenancy & Isolation
*   Every business (Tenant) gets its own "Account ID" on the Operator.
*   The Operator manages multiple WhatsApp sockets simultaneously (e.g., `main-wa`, `tenant-123-wa`).
*   The Database enforces Row-Level Security (RLS) or strict `tenantId` filtering. Tenant A can never see or send messages on Tenant B's WhatsApp socket.

## 5. Safety, Control & Compliance
*   **Super Admin Master Switch:** A database-backed toggle (not an env var) that instantly kills AI processing globally without requiring a redeploy.
*   **Manual Mode:** A per-tenant toggle. If ON, the system logs messages but the AI is forbidden from replying.
*   **POPIA/GDPR:** The system must natively listen for "STOP", "UNSUBSCRIBE", or "OPT-OUT" keywords and instantly add the sender to a blocklist for that specific tenant.

## 6. The User Flow (The "Thandi" Experience)
1.  Tenant signs up on the Main App.
2.  Tenant clicks "Connect WhatsApp". The Main App asks the Engine to create a new socket and returns a QR string.
3.  Tenant scans the QR with their physical phone (once).
4.  Physical phone can now be turned off. The Engine holds the session 24/7.
5.  Customers text the Tenant's number. The Engine receives it, signs it, and POSTs to the Brain. The Brain's AI replies via the Engine.

## Part 4: Architecture – The NahaLabs Patterns

### 4.1 Multi-Tenancy Pattern

- Shared database, `tenant_id` column on every business table.
- Every query helper requires a tenant context; raw unscoped queries are lint-blocked.
- Tenant isolation applies equally to: SQL queries, vector searches, AI tool calls, file storage paths, cache keys, and analytics.
- Automated cross-tenant leak tests run in CI.

### 4.2 AI-Native Pattern

1. **Business rules never live in prompts.** Rules live in services; AI orchestrates services via tool calling.
2. **Grounded by construction.** Every factual claim must originate from a tool call into application data. The model composes language; it never sources facts from weights.
3. **Provider-agnostic via Vercel AI SDK.** A single abstraction routes to any model.
4. **Multi-provider fallback.** Ordered list of providers (Groq → Google → Anthropic → OpenRouter); if one fails, try the next. Log successes and failures for monitoring.

### 4.3 Messaging Platform Pattern (Self-Owned)

- **Two-server architecture**: Core App (Next.js on Vercel) + Operator (Express + Baileys on Render).
- **Communication**: HMAC-signed webhooks between Core and Operator.
- **Database split**: Core uses Prisma/Drizzle for business data; Operator uses raw `pg` for Baileys auth sessions (`wa_sessions`).
- **One live socket per `wa_account_id`** (INV‑1).
- **Bindings** map `(app_id, tenant_id)` to a `wa_account_id`.
- **Inbound**: Operator receives message → persists `platform_event` → fires signed webhook to Core → Core verifies HMAC → persists message → enqueues `PlatformJob` → worker processes (AI) → writes reply to `OutboxMessage`.
- **Outbound**: Outbox dispatcher polls → calls Operator `/send` endpoint (HMAC signed) → Operator sends via Baileys → retries with backoff → dead‑letter after 5 attempts.
- **Observability**: Trace envelope on all logs (`traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`).

### 4.4 Event-Driven Pattern

- Every significant business action emits a domain event, persisted to an `events` table.
- Use `Outbox` pattern to ensure reliable delivery to external systems (WhatsApp, email, webhooks).
- Background jobs use `FOR UPDATE SKIP LOCKED` to lock and process one job at a time, with exponential backoff and dead-letter queues.

### 4.5 Attribution & ROI Measurement Pattern

- **A/B test**: 50/50 split (cookie-based) between control (normal site) and test (AI-enhanced).
- **Single KPI**: Revenue per visitor – cannot be gamed.
- **Baseline**: Calculated from the client's own data (e.g., Shopify export) for the 60 days prior – never your estimate.
- **Attribution**: Tag all AI-generated cart/orders with a `utm_source=ai_stylist` or session ID; join with Shopify `orders/create` webhook.
- **Dashboard**: Real-time, shared with client; they can verify numbers themselves.
- **Audit clause**: If numbers are disputed, an independent auditor re-runs the same query against the client's own data.

NahaLabs AI Engineering Workflow Skill
TAKT-Governed Agentic Software Engineering
Purpose
Use this skill whenever building, modifying, debugging, refactoring, testing, reviewing, or deploying a NahaLabs application with AI coding agents.
The objective is to replace ad-hoc AI coding conversations with a repeatable, controlled, auditable software-engineering workflow.
The governing principle is:
The AI agent writes the code. The workflow decides what happens next.
AI agents are workers. They do not automatically control the engineering process.
The standard lifecycle is:
Requirement → Plan → Build → Review → Test → Fix → Security → Verify → Approval → Merge → Deploy
________________________________________
1. Core Operating Principle
Never allow an AI coding agent to independently decide the entire software-development lifecycle.
Separate:
•	Planning
•	Implementation
•	Review
•	Testing
•	Security review
•	Verification
•	Approval
•	Deployment
The agent may perform assigned work.
The workflow determines whether the agent is allowed to proceed.
The human owner determines the maximum authority granted to the workflow.
________________________________________
2. Authority Model
Every project must have an explicit Agent Authority Boundary.
The owner may grant authority at three levels:
LEVEL 1 — TASK AUTHORITY
The agent may work only on one explicitly defined task.
Example:
Fix the WhatsApp webhook validation bug.
The agent cannot modify unrelated features.
________________________________________
LEVEL 2 — FEATURE AUTHORITY
The agent may work across all files and components required to complete one approved feature.
Example:
Build customer reactivation campaigns.
The agent may modify:
•	frontend
•	backend
•	database
•	API routes
•	tests
but only within the approved feature scope.
________________________________________
LEVEL 3 — APPLICATION AUTHORITY
The agent/workflow may operate across the entire application.
This should be used only when the owner explicitly grants it.
Examples:
•	major refactor
•	dependency migration
•	application-wide testing
•	architecture modernization
•	broad bug-fixing campaign
Never infer application-wide authority from a task-level instruction.
Authority must be explicitly granted.
________________________________________
3. Default Authority
The default authority is:
TASK-SCOPED
Never assume:
"Work on this feature"
means:
"You may change anything in the application."
If broader access is required, stop and request escalation.
Authority should be:
•	explicit
•	visible
•	scoped
•	time-bounded where practical
•	revocable
•	auditable

5. Existing Application — Migration Decision Matrix
For every significant existing component, explicitly classify it as one of:
KEEP
MIGRATE
REWRITE
REMOVE
DEPRECATE
Never automatically rewrite existing functionality.
________________________________________
KEEP
Use when the existing implementation is:
•	technically sound
•	compatible with the target architecture
•	secure
•	maintainable
•	valuable
•	cheaper/safer to retain
Example:
Existing:
Playwright test suite

Decision:
KEEP

Reason:
Already compatible with target testing strategy.
________________________________________
MIGRATE
Use when the functionality is valuable but its implementation needs to move to the target architecture.
Example:
Existing:
Firebase authentication

Target:
Clerk

Decision:
MIGRATE

Reason:
Authentication functionality remains,
but identity infrastructure changes.
________________________________________
REWRITE
Use when the functionality is strategically important but the existing implementation is:
•	fundamentally incompatible
•	fragile
•	difficult to maintain
•	insecure
•	architecturally obsolete
•	more expensive to repair than rebuild
Example:
Existing:
Legacy AI orchestration

Decision:
REWRITE

Reason:
Tightly coupled architecture prevents
integration with the NahaLabs agent layer.
________________________________________
REMOVE
Use when a component:
•	provides no meaningful value
•	duplicates another capability
•	introduces unnecessary complexity
•	creates unacceptable security risk
•	is obsolete
Example:
Existing:
Unused analytics package

Decision:
REMOVE

Reason:
No active usage.
________________________________________
DEPRECATE
Use when the component must remain temporarily for compatibility but should eventually disappear.
Example:
Existing:
Legacy API endpoint

Decision:
DEPRECATE

Plan:
Maintain during migration.
Introduce new endpoint.
Migrate consumers.
Remove after sunset period.

## 🔧 The Skill Prompt (Copy & Paste)

```markdown
# SKILL: Figranium Integration Consultant

## Context
You are an expert in Figranium—a self-hosted, block‑based browser automation platform. Your job is to help me identify whether Figranium can solve automation, monitoring, or data‑extraction challenges in the app I'm building, and to give me a concrete implementation plan.

## The Tool
- **Name**: Figranium
- **Website**: [figranium.dev](https://figranium.dev/)
- **GitHub**: [github.com/figranium/figranium](https://github.com/figranium/figranium)
- **Docs**: [figranium.dev/docs](https://figranium.dev/docs)
- **MCP Integration**: [figranium.dev/mcp](https://figranium.dev/mcp) (lets LLM clients like Claude Desktop and Cursor control Figranium directly)

## Core Capabilities (Always Consider)
Figranium lets you:
- **Build workflows visually** – drag and drop blocks like Click, Type, Scroll, Navigate, Extract, Screenshot
- **Add logic** – if/else, while loops, foreach, variables (`{$varName}`)
- **Trigger via API or schedule** – `POST /api/tasks/:id/api` or cron schedules
- **Run in 3 modes** – Agent (headless), Scrape (lightweight), Headful (VNC debug)
- **Evade detection** – natural typing, cursor glide, proxy rotation, 13‑point fingerprint evasion
- **Capture evidence** – screenshots and .webm video recordings for every run
- **Self‑host everything** – data stays on your infrastructure

## Your Process
When I describe my app, follow this checklist:

1. **Understand the problem** – What manual browser task does my app need to do? (e.g., logging into a portal, scraping data, filling forms, monitoring changes)
2. **Check fit** – Is this a repetitive, browser‑based task that lacks a reliable API?
3. **Design the workflow** – Outline the specific Figranium blocks I would use.
4. **Schedule or API‑trigger** – Should it run on a cron schedule, or be triggered on‑demand via REST API?
5. **Output & alerting** – What data should Figranium return? Should it send alerts (WhatsApp, email, Slack)?
6. **Stealth considerations** – Does this site have anti‑bot protection? If yes, recommend proxy rotation and stealth settings.
7. **Implementation steps** – Give me a clear, actionable plan.

## Output Format
Always structure your response as:

1. **✅ Fit Assessment** – Yes/No and why.
2. **🛠️ Workflow Design** – The blocks I'd use (e.g., Navigate → Wait → Type → Click → Extract → If/Else → Send Alert).
3. **⚙️ Trigger** – Schedule or API.
4. **📤 Output** – What data comes back (JSON, screenshots, video).
5. **🚀 Implementation Steps** – Step‑by‑step to build it.
6. **💡 Pro Tip** – Any extra optimisation or monetisation angle.

---

Now, here is my app / problem:

[PASTE YOUR APP DESCRIPTION HERE]
```

23. Definition of Done
An application is considered automation-ready when:
•	Core functionality works without Make/Zapier
•	Public API exists for important capabilities
•	API is versioned
•	Authentication is implemented
•	Authorization is enforced
•	Tenant isolation works
•	Webhooks exist for important events
•	Webhooks are signed
•	Webhooks retry safely
•	Idempotency is implemented where needed
•	Audit logging exists
•	Rate limiting exists
•	API errors are structured
•	MCP tools are exposed where useful
•	High-impact agent actions require appropriate authorization/confirmation
•	Make integration is implemented where useful
•	Zapier integration is implemented where useful
•	Integration tests exist
•	Documentation exists
•	No secrets are committed
•	No integration has direct database access
•	No core business logic depends on Make or Zapier

Resend Transactional Email Skill
Purpose
Use Resend as the default transactional email infrastructure for this application.
Resend is responsible for programmatic, application-triggered emails. It should
be integrated securely on the server side and treated as infrastructure rather
than as frontend functionality.
Use it for:
•	Welcome emails
•	Email verification
•	Password reset emails
•	Login and security alerts
•	Account notifications
•	Contact form notifications
•	Payment confirmations
•	Invoice emails
•	Subscription notifications
•	Admin alerts
•	Error alerts
•	Customer onboarding emails
•	System-generated reports
•	Background job notifications
Do NOT use Resend for:
•	Bulk marketing campaigns unless explicitly required
•	Spam or unsolicited outreach
•	Client-side email sending
•	Exposing API keys in browser code
________________________________________
Core Architecture Rules
1. Server-side only
The Resend API key MUST never be exposed to the browser.
Never use:

RESEND_API_KEY=re_...
Only call Resend from trusted server-side code such as:
•	Next.js Route Handlers
•	Next.js Server Actions
•	Backend API routes
•	Serverless functions
•	Background workers
•	Trusted backend services

Central Email Service
Create a reusable email service.
import { resend } from "./resend";

interface SendEmailParams {
  to: string | string[];
  subject: string;
  html: string;
  from?: string;
}

export async function sendEmail({
  to,
  subject,
  html,
  from,
}: SendEmailParams) {
  try {
    const { data, error } = await resend.emails.send({
      from:
        from ||
        process.env.EMAIL_FROM ||
        "App <onboarding@resend.dev>",
      to,
      subject,
      html,
    });

    if (error) {
      throw new Error(error.message);
    }

    return data;
  } catch (error) {
    console.error("Email sending failed:", error);

    throw error;
  }
}
Application code should preferably call:
sendEmail()
instead of calling Resend directly everywhere.

51. FINAL INSTRUCTION TO THE CODING AGENT
Whenever I ask you to build a new application or modify an existing application:
1.	Inspect the application before making changes.
2.	Identify the important user and business journeys.
3.	Identify meaningful telemetry events.
4.	Define a consistent event schema.
5.	Implement HTML/browser telemetry where relevant.
6.	Implement WhatsApp telemetry where relevant.
7.	Implement server/API/business events where relevant.
8.	Use deterministic logic before AI.
9.	Use Cron only for naturally scheduled work.
10.	Use AI only where it provides meaningful additional intelligence.
11.	Build intent, scoring, segmentation, prediction, or recommendation capabilities only where justified.
12.	Create an action engine for appropriate automated responses.
13.	Track the outcome of every important action.
14.	Connect actions to revenue or meaningful business KPIs where possible.
15.	Build privacy, consent, security, and tenant isolation into the architecture.
16.	Make important AI decisions explainable.
17.	Make automation auditable.
18.	Make telemetry reliable and non-blocking.
19.	Avoid unnecessary LLM calls.
20.	Do not create AI slop or meaningless tracking.
21.	Do not track users merely because tracking is technically possible.
22.	Prefer simple, deterministic, maintainable engineering over unnecessary complexity.
23.	Reuse the application's existing architecture and infrastructure where practical.
24.	Do not introduce a new third-party analytics platform merely for convenience without first evaluating whether the existing stack can support the requirement.
25.	Before declaring the feature complete, demonstrate the complete path:
EVENT
→ DECISION
→ ACTION
→ OUTCOME
→ KPI / REVENUE
The objective is not to add "telemetry."
The objective is to turn the application into a measurable, adaptive, outcome-driven intelligent system.
UNIVERSAL PRINCIPLE
Observe behaviour. Understand context. Score intent. Apply rules. Use AI where reasoning is needed. Take the next best action. Measure the outcome. Learn from the result.
This architecture should be treated as a reusable engineering capability across all NahaLabs applications.
