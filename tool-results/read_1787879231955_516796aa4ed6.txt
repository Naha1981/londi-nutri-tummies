   702→   702→## 6. Integration Architecture
   703→   703→
   704→   704→**Every external system connects through a dedicated integration client and terminates at a dedicated webhook route.**
   705→   705→
   706→   706→### NahaLabs Messaging Platform (WhatsApp) Standard (ADR-014)
   707→   707→We do not use third-party WhatsApp bridges or SaaS conductors. We own the infrastructure via a custom 2-Server Microservice Architecture.
   708→   708→
   709→   709→**The Architecture:**
   710→   710→1. **Core App (Next.js on Vercel):** Handles UI, AI brain, Prisma database, outbox, and durable jobs.
   711→   711→2. **WhatsApp Operator (Express + `@whiskeysockets/baileys` on Render):** A stateful Docker service that maintains persistent WebSocket connections to WhatsApp.
   712→   712→3. **The Bridge (HMAC v2 Webhooks):** Core and Operator communicate exclusively via signed HTTP endpoints.
   713→   713→
   714→   714→**Database Split (Crucial):**
   715→   715→- **Core App:** Uses Prisma/Drizzle for all business data (`tenants`, `messages`, `OutboxMessage`, `PlatformJob`).
   716→   716→- **Operator:** Uses raw `pg` (node-postgres) for Baileys auth sessions (`wa_sessions` table) to handle `BufferJSON` serialization. The Operator auto-creates its tables on boot.
   717→   717→
   718→   718→**Identity & Multi-Tenancy:**
   719→   719→- Fundamental identity is `wa_account_id` (one connected WhatsApp number).
   720→   720→- One credential state per account (`wa_sessions` PK: `wa_account_id, key`).
   721→   721→- **INV-1:** ONE live socket per `wa_account_id`, regardless of how many apps/tenants bind to it.
   722→   722→- Bindings (`wa_account_bindings`) map `(app_id, tenant_id)` to a `wa_account_id`.
   723→   723→
   724→   724→**Inbound Flow (Customer → AI):**
   725→   725→1. Operator receives message → persists `platform_event` → creates idempotent `inbound_delivery` per active binding.
   726→   726→2. Operator fires signed webhook (HMAC v2: timestamp + nonce + raw body signature) to Core App.
   727→   727→3. Core App verifies HMAC → persists inbound message → enqueues `PlatformJob` → returns 200 fast.
   728→   728→4. Durable Job Worker (PostgresWorker with `FOR UPDATE SKIP LOCKED`) processes job → runs AI Revenue Employee (Vercel AI SDK) → writes reply to `OutboxMessage`.
   729→   729→
   730→   730→**Outbound Flow (AI → Customer):**
   731→   731→1. Outbox Dispatcher worker polls `OutboxMessage` (with `SKIP LOCKED`).
   732→   732→2. Calls Operator `/send` endpoint (signed with HMAC v2).
   733→   733→3. Operator sends via Baileys socket → updates delivery status → retries with backoff → dead-letters after 5 attempts.
   734→   734→
   735→   735→**Security & Observability:**
   736→   736→- HMAC v2 on all Core ↔ Operator traffic. Constant-time comparison (`crypto.timingSafeEqual`).
   737→   737→- QR codes are ephemeral (Redis/in-memory TTL), never stored in Postgres.
   738→   738→- Trace envelope on all logs: `traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`.
   739→   739→- Business code calls `sendMessage(...)` via a typed client (`src/lib/messaging/platform-client.ts`). It never imports Baileys or transport-specific methods.
   740→   740→
   741→   741→### Payments standard
   742→   742→- Providers (PayFast, Stripe) live behind a common payment abstraction.
   743→   743→- **Browser redirects are never payment confirmation. Provider webhooks are the sole source of truth.** Verify signature, source, and amount before updating order state.
