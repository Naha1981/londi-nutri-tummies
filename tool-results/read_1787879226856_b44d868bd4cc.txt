    24→CORE PRINCIPLE: NEVER TRUST THE NARRATIVE. VERIFY THE REAL SYSTEM.
    25→Do not assume that:
    26→•       a feature exists because someone said it exists
    27→•       code works because an AI said it works
    28→•       a commit exists because a previous session reported it
    29→•       tests pass because a report says they passed
    30→•       an environment variable is configured because documentation mentions it
    31→•       a deployment succeeded because the dashboard is green
    32→•       a cron job exists because code contains a cron route

   108→For every important domain, identify the single authoritative source.
   109→Domain  Source of Truth

   111→Tenant ownership        Database

   127→PART 5 — BEFORE IMPLEMENTATION: WRITE THE PLAN
   128→Do not jump directly into code. Produce:
   129→OBJECTIVE — What exact problem is being solved?
   130→NON-GOALS — What is explicitly not being changed?
   131→ASSUMPTIONS — Which assumptions need verification?
   132→RISKS — Ranked: CRITICAL / HIGH / MEDIUM / LOW
   133→FILES EXPECTED TO CHANGE — List likely files.
   134→DATA CHANGES — schema changes, migrations, indexes, constraints, backfills, rollback concerns.
   135→API CONTRACT CHANGES — Request / Response / Success / Failure / Authentication / Authorization / Idempotency.
   136→TEST PLAN — Unit / Integration / Seam / Failure / Security / Regression / Mutation (where appropriate).
   137→Do not implement until the plan is clear.

   139→PART 6 — USE GATES
   140→Divide large work into bounded engineering gates.
   141→G0.1 — Security boundary
   142→G0.2 — Configuration safety
   143→G0.3 — Reliability and failure recovery
   144→G1   — Pilot readiness
   145→G2   — Production readiness
   146→G3   — Scale readiness
   147→Each gate must define:
   148→Objective · Scope · Non-goals · Baseline · Files changed · Risks
   149→Tests · Verification commands · Deployment impact
   150→Rollback considerations · PASS / FAIL criteria
   151→Do not mix unrelated fixes into one gate.
   152→________________________________________
   153→PART 7 — CODE CHANGE RULES
   154→Make the smallest correct change.
   155→Do not:
   156→•       rewrite unrelated modules
   157→•       refactor for aesthetics during a production fix
   158→•       upgrade dependencies unnecessarily
   159→•       rename unrelated files
   160→•       introduce frameworks because they are fashionable
   161→Prefer: Minimal · Scoped · Reversible · Testable · Observable
   162→________________________________________
   163→PART 8 — SECURITY ARCHITECTURE
   164→Every security boundary must fail closed.
   165→Authentication
   166→•       Bad: No secret? Accept request.
   167→•       Good: No secret? Reject request.
   168→Authorization — Always verify:
   169→•       Who is making this request?
   170→•       What are they allowed to access?
   171→•       Which tenant owns this resource?
   172→Never trust:
   173→•       tenant IDs from arbitrary clients
   174→•       account ownership claimed in webhook payloads
   175→•       user role claims without verification
   176→•       query parameters as proof of identity
   177→Derive ownership from authoritative database relationships — not client-supplied data.
   178→________________________________________
   179→PART 9 — WEBHOOKS
   180→For every webhook:
   181→1.      Verify signature.
   182→2.      Fail closed.
   183→3.      Use constant-time comparison where appropriate.
   184→4.      Validate payload structure.
   185→5.      Derive ownership from trusted records.
   186→6.      Implement idempotency.
   187→7.      Handle retries safely.
   188→8.      Avoid duplicate side effects.
   189→VERIFY → VALIDATE → RESOLVE AUTHORITATIVE OWNERSHIP →
   190→CHECK IDEMPOTENCY → RECORD EVENT → PROCESS → RETURN CLEAR RESPONSE
   191→Never generate irreversible side effects before idempotency is established.
   192→________________________________________
   193→PART 10 — DATABASE ENGINEERING
   194→Before changing the schema, determine:
   195→Does existing data remain valid?
   196→Does the migration lock the table?
   197→Is the change additive?
   198→Can old and new code coexist during rollout?
   199→Does deployment ordering matter?
   200→Is rollback possible?
   201→Are indexes required?
   202→Are uniqueness constraints required?
   203→Prefer additive migrations, e.g. ADD COLUMN IF NOT EXISTS.
   204→Use nullable columns for backward compatibility where appropriate, apply defaults carefully, use partial indexes where appropriate, and enforce real invariants with unique constraints.
   205→Critical invariants belong in the database — never rely only on application-level race prevention.
   206→________________________________________
   207→PART 11 — IDEMPOTENCY AND CONCURRENCY
   208→Assume systems will retry. Assume:
   209→•       webhooks duplicate
   210→•       workers restart
   211→•       networks time out
   212→•       processes crash
   213→•       requests overlap
   214→•       queues deliver more than once
   215→Use: Idempotency keys · Unique constraints · UPSERT / ON CONFLICT · Outbox pattern · Transactional boundaries
   216→Ask: What happens if this operation runs twice? Then: What happens if two copies run simultaneously?
   217→________________________________________
   218→PART 12 — OUTBOX AND ASYNCHRONOUS WORK
   219→For external side effects:
   220→DATABASE EVENT → DURABLE JOB → WORKER → EXTERNAL SYSTEM → SUCCESS/FAILURE RECORDED
   221→Do not make a database write appear successful if the external action silently disappeared. Every important asynchronous operation should have observable state: pending → processing → queued → sent → delivered → failed.
   222→Do not display success unless success is actually known.
   223→________________________________________
   224→PART 13 — UI TRUTHFULNESS
   225→The UI must reflect reality. Never show ✓ Delivered unless delivery is known. Use explicit states: Sending / Queued / Delivered / Failed / Unknown.
   226→Historical data without a known state should remain unknown — do not fabricate green indicators.
   227→________________________________________
   228→PART 14 — ERROR HANDLING
   229→Every critical failure should answer:
   230→What failed?
   231→Why did it fail?
   232→Can the user act on it?
   233→Can the system retry?
   234→Will the failure be visible?
   235→Avoid return { ok: true } when nothing actually happened. Success must mean the defined success contract occurred — not merely that no exception was thrown.
   236→________________________________________
   237→PART 15 — TESTING PYRAMID
   238→Test every significant change at the appropriate level.
   239→Unit tests — pure logic (Input → Decision → Output)
   240→Integration tests — components together (API → Service → Database)
   241→Seam tests — confirm real modules are actually wired together:
   242→Route → Dispatch helper → Outbox → Worker → Database state → UI
   243→Seam tests prevent: "The helper works perfectly, but the real route never calls it."
   244→________________________________________
   245→PART 16 — FAILURE TESTING
   246→Do not test only happy paths. Deliberately simulate:
   247→Missing environment variable    Timeout                Null foreign key
   248→Invalid secret                  Duplicate webhook       Worker crash
   249→Database unavailable            Disconnected account    Retry exhaustion
   250→External API failure            Malformed payload       Unauthorized user
   251→                                                          Race condition
   252→The most important test is often: the exact failure that caused the last bug.
   253→________________________________________
   254→PART 17 — MUTATION TESTING MINDSET
   255→For critical logic, deliberately break it:
   256→Change success to true.
   257→Disable a guard.
   258→Remove a condition.
   259→Skip reconciliation.
   260→Treat "queued" as "delivered."
   261→Then confirm the tests fail. The stronger question isn't "Do tests pass?" — it's "Would the tests catch the bug returning?"
   262→________________________________________
   263→PART 18 — DEPENDENCY MANAGEMENT
   264→Do not upgrade dependencies casually. Before upgrading, ask:
   265→Why is this dependency changing?
   266→What vulnerability does it fix?
   267→Is the vulnerability reachable in our code?
   268→What code path is affected?
   269→What is the upgrade risk?
   270→What breaking changes exist?
   271→Maintain an ADR for meaningful dependency decisions.
   272→________________________________________
   273→PART 19 — ARCHITECTURE DECISION RECORDS (ADRs)
   274→Create an ADR for any decision future engineers may question.
   275→# ADR-XXXX — Title
   276→Status:
   277→Date:
   278→
   279→Context: What problem exists?
   280→Decision: What was chosen?
   281→Alternatives: What else was considered?
   282→Consequences: Benefits / Risks / Operational impact
   283→Review trigger: When should this be reconsidered?
   284→Examples: provider architecture choices, self-hosted vs. SaaS dependency, database choice, auth provider, queue architecture, dependency upgrade deferral.
   285→________________________________________
   286→PART 20 — SELF-HOSTED TOOLS POLICY
   287→Evaluate every new tool in this order:
   288→1. Can we use the existing stack? Don't add infrastructure unnecessarily.
   289→2. Open source / self-hosted — prefer when: recurring SaaS cost is significant, sensitive data should stay under our control, the tool is core infrastructure, vendor lock-in is dangerous, or deployment complexity is acceptable.
   290→3. Managed services — prefer when: uptime burden exceeds our operational capacity, security operations are complex, the service isn't our competitive advantage, or self-hosting would cost more in engineering time than it saves.
   291→Self-host strategically. Do not self-host for ego.

   312→________________________________________
   313→PART 22 — COMMIT DISCIPLINE
   314→Each commit represents one coherent engineering change.
   315→Good:
   316→fix(webhook): fail closed when secret is missing
   317→fix(outbox): reconcile message delivery failures
   318→test(dispatch): add exhaustive failure matrix
   319→docs(adr): document dependency risk decision
   320→Avoid: final fixes, updates, working now, stuff
   321→Before committing: git diff and git status — review exactly what changed. After committing: git show --stat and git show — verify the commit contains what you intended.

   323→PART 23 — BRANCH STRATEGY
   324→Use branches for bounded work:
   325→main → feature/gate-name → test → review → merge
   326→Before merging, verify: ancestry, tests, diff, deployment implications, migrations, and environment requirements. Never merge based only on a summary.
   327→________________________________________
   328→PART 24 — DEPLOYMENT ARCHITECTURE
   329→Before deploying, identify: frontend host, backend host, database, worker, cron scheduler, queue, environment variables, secrets, domains, webhooks, health checks, readiness checks, logs, monitoring.
   330→Then sequence the deployment:
   331→1. Configure environment variables
   332→2. Deploy application
   333→3. Deploy worker/operator
   334→4. Run migration
   335→5. Verify health
   336→6. Verify readiness
   337→7. Verify cron auth
   338→8. Configure scheduler
   339→9. Prove scheduler runs repeatedly
   340→10. Connect external services
   341→11. Run end-to-end test
   342→________________________________________
   343→PART 25 — HEALTH VS. READINESS
   344→Do not confuse the two.
   345→Liveness — Is the process alive? → /health
   346→Readiness — Can this service actually perform its job? → /ready
   347→A service may be alive but not ready. Design and monitor them separately.
   348→________________________________________
   349→PART 26 — CRON AND SCHEDULER VERIFICATION
   350→A cron route existing does not mean cron is running. For every scheduled job, verify the full chain:
   351→Endpoint exists → Correct HTTP method → Auth works → Unauthorized calls fail →
   352→Authorized calls succeed → Scheduler is configured → Scheduler history shows
   353→repeated success → Jobs actually process → Queue depth stays healthy
   354→Configured ≠ running. Running ≠ processing. Processing ≠ succeeding. Verify the entire chain.
   355→________________________________________
   356→PART 27 — OBSERVABILITY
   357→Every production system should be able to answer:
   358→Is it running?          Are jobs accumulating?
   359→Is it healthy?           Are retries increasing?
   360→Is it ready?              Are failures visible?
   361→                           Which tenant is affected?
   362→                           Which dependency is failing?
   363→At minimum, provide: structured logs, error visibility, health endpoint, readiness endpoint, queue monitoring, failure state, deployment logs, and runbooks.
   364→________________________________________
   365→PART 28 — PRODUCTION SMOKE TEST
   366→After deployment, test one real end-to-end user journey. Example, for a messaging system:
   367→REAL USER → REAL EXTERNAL MESSAGE → WEBHOOK → AUTHENTICATION →
   368→DATABASE → AI / BUSINESS LOGIC → OUTBOX → WORKER →
   369→EXTERNAL DELIVERY → DATABASE RECONCILIATION → UI
   370→Do not declare production readiness until the real journey succeeds end to end.
   371→________________________________________
   372→PART 29 — OPERATIONAL RUNBOOK
   373→Every production app needs a runbook covering:
   374→How to deploy · How to migrate · How to rollback · How to rotate secrets
   375→How to inspect failures · How to restart workers · How to verify cron
   376→How to verify external integrations · How to recover stuck jobs
   377→Who can access admin operations
   378→A production system must be operable by someone who did not write the original code.

   702→## 6. Integration Architecture
   703→
   704→**Every external system connects through a dedicated integration client and terminates at a dedicated webhook route.**
   705→
   706→### NahaLabs Messaging Platform (WhatsApp) Standard (ADR-014)
   707→We do not use third-party WhatsApp bridges or SaaS conductors. We own the infrastructure via a custom 2-Server Microservice Architecture.
   708→
   709→**The Architecture:**
   710→1. **Core App (Next.js on Vercel):** Handles UI, AI brain, Prisma database, outbox, and durable jobs.
   711→2. **WhatsApp Operator (Express + `@whiskeysockets/baileys` on Render):** A stateful Docker service that maintains persistent WebSocket connections to WhatsApp.
   712→3. **The Bridge (HMAC v2 Webhooks):** Core and Operator communicate exclusively via signed HTTP endpoints.
   713→
   714→**Database Split (Crucial):**
   715→- **Core App:** Uses Prisma/Drizzle for all business data (`tenants`, `messages`, `OutboxMessage`, `PlatformJob`).
   716→- **Operator:** Uses raw `pg` (node-postgres) for Baileys auth sessions (`wa_sessions` table) to handle `BufferJSON` serialization. The Operator auto-creates its tables on boot.
   717→
   718→**Identity & Multi-Tenancy:**
   719→- Fundamental identity is `wa_account_id` (one connected WhatsApp number).
   720→- One credential state per account (`wa_sessions` PK: `wa_account_id, key`).
   721→- **INV-1:** ONE live socket per `wa_account_id`, regardless of how many apps/tenants bind to it.
   722→- Bindings (`wa_account_bindings`) map `(app_id, tenant_id)` to a `wa_account_id`.
   723→
   724→**Inbound Flow (Customer → AI):**
   725→1. Operator receives message → persists `platform_event` → creates idempotent `inbound_delivery` per active binding.
   726→2. Operator fires signed webhook (HMAC v2: timestamp + nonce + raw body signature) to Core App.
   727→3. Core App verifies HMAC → persists inbound message → enqueues `PlatformJob` → returns 200 fast.
   728→4. Durable Job Worker (PostgresWorker with `FOR UPDATE SKIP LOCKED`) processes job → runs AI Revenue Employee (Vercel AI SDK) → writes reply to `OutboxMessage`.
   729→
   730→**Outbound Flow (AI → Customer):**
   731→1. Outbox Dispatcher worker polls `OutboxMessage` (with `SKIP LOCKED`).
   732→2. Calls Operator `/send` endpoint (signed with HMAC v2).
   733→3. Operator sends via Baileys socket → updates delivery status → retries with backoff → dead-letters after 5 attempts.
   734→
   735→**Security & Observability:**
   736→- HMAC v2 on all Core ↔ Operator traffic. Constant-time comparison (`crypto.timingSafeEqual`).
   737→- QR codes are ephemeral (Redis/in-memory TTL), never stored in Postgres.
   738→- Trace envelope on all logs: `traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`.
   739→- Business code calls `sendMessage(...)` via a typed client (`src/lib/messaging/platform-client.ts`). It never imports Baileys or transport-specific methods.
   740→
   741→### Payments standard
   742→- Providers (PayFast, Stripe) live behind a common payment abstraction.
   743→- **Browser redirects are never payment confirmation. Provider webhooks are the sole source of truth.** Verify signature, source, and amount before updating order state.

   932→# How the NahaLabs Messaging Platform Actually Works (Plain English)
   933→
   934→Imagine you own a hair salon. A customer WhatsApps your business number asking "How much for balayage?"
   935→
   936→Here's exactly what happens in the next 3 seconds:
   937→
   938→---
   939→
   940→## The Two-Server Setup (Like a Restaurant)
   941→
   942→Think of it like a restaurant with a **front-of-house** and a **back-of-house**:
   943→
   944→**1. The Front-of-House (Vercel - Your Main App)**
   945→- This is what you and your staff see: the dashboard, the AI brain, the customer database, the payment system
   946→- It's like the dining room and the manager's office
   947→- It's fast, stateless, and runs on Vercel (serverless)
   948→
   949→**2. The Back-of-House (Render - The WhatsApp Operator)**
   950→- This is a dedicated server that stays logged into WhatsApp 24/7 (using Baileys, the same library WhatsApp Web uses)
   951→- It's like the kitchen — it handles the heavy, persistent work of actually sending and receiving WhatsApp messages
   952→- It runs on Render (a Docker container that never sleeps)
   953→
   954→**They talk to each other via secure, signed webhooks** (like a kitchen ticket system with security seals).
   955→
   956→---
   957→
   958→## What Happens When a Customer Messages You
   959→
   960→**Step 1: Customer sends a message**
   961→- Customer texts "How much for balayage?" to your salon's WhatsApp number
   962→
   963→**Step 2: The Back-of-House receives it**
   964→- The WhatsApp Operator (on Render) is logged into your WhatsApp account and sees the message instantly
   965→- It records the message in a database table called `platform_events`
   966→- It checks which apps are allowed to see this message (in your case, just 2ndLife for your salon)
   967→
   968→**Step 3: The Back-of-House sends a secure ticket to the Front-of-House**
   969→- The Operator creates a signed webhook (like a tamper-proof receipt with a timestamp and security code)
   970→- It sends this to your main app on Vercel via a webhook endpoint
   971→
   972→**Step 4: The Front-of-House verifies and processes**
   973→- Your main app receives the webhook
   974→- It verifies the security signature (HMAC v2) to make sure it's really from your Operator and not a hacker
   975→- It saves the inbound message to your database
   976→- It creates a "job" for the AI to process (like putting an order ticket on the kitchen rail)
   977→
   978→**Step 5: The AI Brain thinks**
   979→- A background worker picks up the job
   980→- It loads your salon's "Business Brain" (your services, prices, brand voice, compliance rules)
   981→- It calls the Vercel AI SDK (which routes to GPT-4o-mini or another model)
   982→- The AI generates a reply: "Balayage starts at R1,200 for medium-length hair. Would you like to book a consultation?"
   983→
   984→**Step 6: The reply goes to the Outbox**
   985→- The AI's reply is saved to an `OutboxMessage` table with status "queued"
   986→- This is like putting the finished dish on the pass, ready to be served
   987→
   988→**Step 7: The Outbox Dispatcher sends it**
   989→- A worker polls the outbox every minute (via cron-job.org or Vercel Cron)
   990→- It picks up your queued message
   991→- It sends a signed request back to the WhatsApp Operator: "Send this text to +27821234567"
   992→
   993→**Step 8: The Back-of-House delivers it**
   994→- The Operator receives the request, verifies the signature
   995→- It uses the Baileys socket (still logged into your WhatsApp) to send the message
   996→- The customer sees the reply in their WhatsApp app
   997→
   998→**Total time: 2-5 seconds from customer message to AI reply.**

  1002→## How Multi-Tenancy Works (Why This Scales)
  1003→
  1004→Imagine you have 100 salon clients, each with their own WhatsApp number.
  1005→
  1006→**The magic is in the `wa_account_id`:**
  1007→- Each WhatsApp number gets a unique account ID
  1008→- The Operator maintains **one live socket per account** (so 100 sockets total)
  1009→- Each socket is locked with a Redis key so if you restart the server, only one instance can claim each socket (prevents duplicate connections)
  1010→
  1011→**Bindings map accounts to tenants:**
  1012→- Your salon's WhatsApp account (`wa_account_id: "abc123"`) is bound to your tenant (`tenant_id: "salon-456"`)
  1013→- When a message comes in, the Operator checks the bindings table to know which app/tenant should receive it
  1014→- Your salon's data never touches another salon's data (tenant isolation at the database level)
  1015→
  1016→**What happens if you launch a second app (Flavourly)?**
  1017→- Flavourly can bind to the **same** WhatsApp account
  1018→- When a message comes in, the Operator fans out the delivery to both 2ndLife and Flavourly
  1019→- Each app processes the message independently with its own AI and business logic
  1020→- One WhatsApp number, multiple apps — no duplicate sockets

  1024→## Why This Is Better Than Evolution API or NoClick
  1025→
  1026→**vs. Evolution API:**
  1027→- Evolution API is a heavy, third-party platform that wraps Baileys
  1028→- You'd be paying for (or managing) their infrastructure, their updates, their breaking changes
  1029→- With the custom Operator, you own the socket directly — no middleman, no dependency, no "Evolution API is down so my app is down"

  1074→# UNIVERSAL WHATSAPP ARCHITECTURE (Direct / No Twilio)
  1075→
  1076→**Role for AI:** You are an expert backend architect building a multi-tenant SaaS with a direct, un-official WhatsApp Web integration. You will **never** use Twilio, Evolution API, 360dialog, or paid WhatsApp Cloud APIs. You will use the "Linked Devices" WebSocket architecture.
  1077→
  1078→## 1. The Two-Component Split (Crucial Rule)
  1079→Never put the WhatsApp socket connection in the same codebase/host as the serverless frontend.
  1080→*   **The Brain (Main App):** Next.js on Vercel (Serverless). Handles UI, Auth (Clerk), Database (Neon/Postgres), Tenant isolation, AI logic, and Webhook receivers.
  1081→*   **The Engine (Operator):** Node.js + `@whiskeysockets/baileys` on Render/Docker/Fly.io (Persistent). Holds the 24/7 WebSocket connection to WhatsApp. Survives server restarts.
  1082→
  1083→## 2. The Engine (Operator) Responsibilities
  1084→*   **Auth:** Generates QR codes for Linked Devices. Saves the cryptographic session state (creds) encrypted into the Main App's database.
  1085→*   **Listening:** Listens to the WhatsApp WebSocket. When a message arrives, it forwards it to the Main App.
  1086→*   **Sending:** Exposes a REST API (`POST /send`) so the Main App can tell it to deliver a message.
  1087→*   **Health:** Exposes `GET /health` for the Main App to monitor uptime.
  1088→
  1089→## 3. The Handshake (Security & Communication)
  1090→*   **Engine to Brain (Inbound):** The Operator `POST`s inbound messages to the Main App's webhook (`/api/webhooks/whatsapp`). **Must be secured with HMAC-SHA256 signatures** so the Brain knows the message is real and not spoofed.
  1091→*   **Brain to Engine (Outbound):** The Main App sends messages by calling the Operator's REST API. Secured via a shared `OPERATOR_API_KEY` in the headers.
  1092→
  1093→## 4. Multi-Tenancy & Isolation
  1094→*   Every business (Tenant) gets its own "Account ID" on the Operator.
  1095→*   The Operator manages multiple WhatsApp sockets simultaneously (e.g., `main-wa`, `tenant-123-wa`).
  1096→*   The Database enforces Row-Level Security (RLS) or strict `tenantId` filtering. Tenant A can never see or send messages on Tenant B's WhatsApp socket.
  1097→
  1098→## 5. Safety, Control & Compliance
  1099→*   **Super Admin Master Switch:** A database-backed toggle (not an env var) that instantly kills AI processing globally without requiring a redeploy.
  1100→*   **Manual Mode:** A per-tenant toggle. If ON, the system logs messages but the AI is forbidden from replying.
  1101→*   **POPIA/GDPR:** The system must natively listen for "STOP", "UNSUBSCRIBE", or "OPT-OUT" keywords and instantly add the sender to a blocklist for that specific tenant.
  1102→
  1103→## 6. The User Flow (The "Thandi" Experience)
  1104→1.  Tenant signs up on the Main App.
  1105→2.  Tenant clicks "Connect WhatsApp". The Main App asks the Engine to create a new socket and returns a QR string.
  1106→3.  Tenant scans the QR with their physical phone (once).
  1107→4.  Physical phone can now be turned off. The Engine holds the session 24/7.
  1108→5.  Customers text the Tenant's number. The Engine receives it, signs it, and POSTs to the Brain. The Brain's AI replies via the Engine.

  1329→## Part 4: Architecture – The NahaLabs Patterns
  1330→
  1331→### 4.1 Multi-Tenancy Pattern
  1332→
  1333→- Shared database, `tenant_id` column on every business table.
  1334→- Every query helper requires a tenant context; raw unscoped queries are lint-blocked.
  1335→- Tenant isolation applies equally to: SQL queries, vector searches, AI tool calls, file storage paths, cache keys, and analytics.
  1336→- Automated cross-tenant leak tests run in CI.
  1337→
  1338→### 4.2 AI-Native Pattern
  1339→
  1340→1. **Business rules never live in prompts.** Rules live in services; AI orchestrates services via tool calling.
  1341→2. **Grounded by construction.** Every factual claim must originate from a tool call into application data. The model composes language; it never sources facts from weights.
  1342→3. **Provider-agnostic via Vercel AI SDK.** A single abstraction routes to any model.
  1343→4. **Multi-provider fallback.** Ordered list of providers (Groq → Google → Anthropic → OpenRouter); if one fails, try the next. Log successes and failures for monitoring.
  1344→
  1345→### 4.3 Messaging Platform Pattern (Self-Owned)
  1346→
  1347→- **Two-server architecture**: Core App (Next.js on Vercel) + Operator (Express + Baileys on Render).
  1348→- **Communication**: HMAC-signed webhooks between Core and Operator.
  1349→- **Database split**: Core uses Prisma/Drizzle for business data; Operator uses raw `pg` for Baileys auth sessions (`wa_sessions`).
  1350→- **One live socket per `wa_account_id`** (INV‑1).
  1351→- **Bindings** map `(app_id, tenant_id)` to a `wa_account_id`.
  1352→- **Inbound**: Operator receives message → persists `platform_event` → fires signed webhook to Core → Core verifies HMAC → persists message → enqueues `PlatformJob` → worker processes (AI) → writes reply to `OutboxMessage`.
  1353→- **Outbound**: Outbox dispatcher polls → calls Operator `/send` endpoint (HMAC signed) → Operator sends via Baileys → retries with backoff → dead‑letter after 5 attempts.
  1354→- **Observability**: Trace envelope on all logs (`traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`).
  1355→
  1356→### 4.4 Event-Driven Pattern
  1357→
  1358→- Every significant business action emits a domain event, persisted to an `events` table.
  1359→- Use `Outbox` pattern to ensure reliable delivery to external systems (WhatsApp, email, webhooks).
  1360→- Background jobs use `FOR UPDATE SKIP LOCKED` to lock and process one job at a time, with exponential backoff and dead-letter queues.
  1361→
  1362→### 4.5 Attribution & ROI Measurement Pattern
  1363→
  1364→- **A/B test**: 50/50 split (cookie-based) between control (normal site) and test (AI-enhanced).
  1365→- **Single KPI**: Revenue per visitor – cannot be gamed.
  1366→- **Baseline**: Calculated from the client's own data (e.g., Shopify export) for the 60 days prior – never your estimate.
  1367→- **Attribution**: Tag all AI-generated cart/orders with a `utm_source=ai_stylist` or session ID; join with Shopify `orders/create` webhook.
  1368→- **Dashboard**: Real-time, shared with client; they can verify numbers themselves.
  1369→- **Audit clause**: If numbers are disputed, an independent auditor re-runs the same query against the client's own data.
